# Skill Optimizer

## 目标与边界

把 Skill 当成可执行产品，以一条可复核证据链完成诊断和优化：

`权威源码 → 发行载荷 → Agent 安装入口/软链 → Agent 实际加载 → 真实任务`

一个规则、资源和版本坐标只有一个主人；开发、发行、安装和运行职责分离。依赖允许存在，但必须说明用途、阶段、体积、引入路径和替代边界。优化不能删除必要的正确性、安全、权限、许可证、来源或用户入口。

每次只处理一个目标 Skill。范围外问题记录证据和建议，不擅自扩大修改面。

## 选择模式

- 用户说“审计、诊断、评估”时保持只读，只交付问题、影响、证据和建议。
- 用户说“优化、精简、修复”时先给人话方案；用户明确确认后才修改。
- 用户尚未确认时，不写文件、不删除内容、不自动修软链，也不展示大段 diff。
- 目标用户、核心任务或输出合同需要改变时，说明这已是新 Skill，改用 `skill-creator`，不静默重建。

## 先读哪份规则

审计软链、发行 manifest、版本、死重或结构时，必须按需读取 [生命周期审计判据](references/lifecycle-audit.md)。它定义证据图、引用入边、候选分类、结构矩阵、阻断级别和死重确认流程。

检查 Codex 或 RedSkill 的 frontmatter/目录政策时，再读取 [平台 Schema Profile](references/platform-schemas.md)。平台推荐结构与通用正确性分开报告；RedSkill 的上传白名单、identifier、审核阈值和线上版本仍归 `redskill-pack`，不迁入本 Skill。

## 建立问题合同

先用事实回答：谁维护、谁发布、谁安装、谁执行；目标路径属于源码、发行、安装还是尚未确定；预期行为、实际行为、最小复现和失败信号是什么。

至少分开核对：

- 权威源码及 Git HEAD/dirty；本地 upstream 不是实时远端，需要当前远端事实时才只读查询。
- 发行目录或压缩包、发行 manifest、`source_commit` 与文件哈希。
- 每个 Agent 的入口原路径、`readlink` 每一跳和最终 `realpath`。
- 安装副本是否为软链、共享目录或独立副本，内容是否漂移。
- Agent 是否真的加载该 Skill 并完成代表任务；静态解析成功不能冒充真实运行成功。

不通过目录名猜开发仓或发行仓。只有目标本身是显式 `source`、显式 `--source`，或发行 manifest 的可信关系能确立权威边。发现无关未提交改动时保留；与目标重叠且无法安全区分时暂停确认。

## 先运行只读审计

```bash
python3 <本 Skill 目录>/scripts/audit_skill.py <目标 Skill 目录> \
  --surface <auto|source|release|installed> \
  --profile <auto|general|review> \
  --schema-profile <auto|codex|redskill> \
  --source <权威源码 Skill 目录> \
  --release-manifest <发行 manifest 路径> \
  --agent-entry codex=<Codex 安装入口> \
  --agent-entry agents=<Agents 安装入口> \
  --supported-node-majors 22,24 \
  --metafile <esbuild metafile 路径> \
  --format json
```

除目标目录外，其余参数按证据可用性提供：

- `--surface auto` 不确立发行或安装权威，因此不输出可删除候选。
- `--profile auto` 在 `release` 使用 `review`，其他载体使用 `general`。
- `--schema-profile auto` 保持 Codex 合同；只有显式目标为 RedSkill 时使用 `redskill`。
- `--agent-entry` 可重复；逐条解析，禁止依赖 shell 空格分词生成或修复软链。
- `--supported-node-majors` 由调用方按当前官方支持矩阵传入；审计器离线运行，不把内置值冒充实时事实。
- 未提供 metafile 时只查找常见文件名。未知 Skill 的 doctor/build/install 不自动执行，不联网、不安装依赖、不自动修改或删除内容。

审计结果在既有 findings/summary/surfaces/metrics 外增加：

- `lifecycle`：源码、发行、安装入口的节点、边和逐跳解析。
- `version_coordinates`：Git、manifest、文件哈希、frontmatter、安装副本分别记录。
- `runtime_verification`：只允许 `not-run / passed / failed`；静态审计固定为 `not-run`。
- `reachability`：功能、文档、发行、完整性、来源、法律入边和保守分类。
- `structure`：逐项规则、状态和证据；不输出含糊总分。

退出码保持兼容：`0` 表示没有确定性结构阻断，`1` 表示断链、循环、非法入口、哈希破坏等已证实阻断，`2` 表示参数、路径或审计运行失败。候选、结构建议和平台政策警告不导致退出码 `1`。

## 形成系统性结论

沿生命周期证据图定位表面症状、直接原因、公共根因和促成条件，再枚举共享同一规则主人或失败机制的入口。以下结论不能互相替代：

- 在 Git 中保留，不等于进入发行包。
- 进入发行包，不等于模型会读取或运行会调用。
- 被 manifest 列出，不等于有功能用途。
- `realpath` 正确，不等于 Agent 已成功调用。
- Git SHA、frontmatter 语义版本和平台线上版本不是同一个版本数字。
- 静态零有效入边只产生 `deadweight-candidate`，不产生“已确认可删”。

依赖按开发/测试、构建/CI、发布打包、用户运行时和可选能力分类。替代顺序是“系统原生能力 → 已有依赖 → 新增依赖”，但只有调用路径、功能等价和回归证据同时成立才建议替代；审计器不自动删除依赖。

出现以下任一情况，不得称为系统性修复：只补用户点名的一个入口；把开发仓直接当用户包；把测试、生成器、大文件或未读文档简单称为无用；仅凭 manifest、来源标签或文件名确认用途；借发行瘦身改变权威源码；用 fallback 掩盖错误合同；用结构审计或一次成功输出代替新 Agent 的真实任务。

## 先给人话方案

```markdown
结论：<整体问题和处理方向>
根因：<公共根因及证据；未证实时写待验证>
生命周期：<源码、发行、安装入口、实际加载和真实任务分别是什么状态>
版本坐标：<Git、manifest、frontmatter、安装副本分别是什么，不混写>
保留：<运行核心、用户发行外壳、开发资产、法律与来源内容>
候选：<死重/依赖/结构候选，载体、体积、有效入边、置信度和所需验证>
要处理：<确认后准备修改的权威位置；不自动修软链>
为何不是补丁：<规则主人、同类影响面和防复发门禁>
风险：<尚未验证的平台、Agent、动态加载或发行链>

```

不要默认罗列提交图、原始 JSON 或大段 diff。对每个文件和依赖，先说明留在 Git、进入发行、运行必需、用户外壳、开发专用、归档或待验证，再讨论移动、排除或删除。

## 用户确认后实施

1. 重新检查 Git 状态、目标路径、各 Agent 入口和发行证据，确认边界没有变化。
2. 在唯一规则主人上做最小完整改动；同一根因散落多处时一次收敛，范围外保持不变。
3. 开发资产留在源码，发行包排除已证实的开发专用内容；保留优化前已有且仍有效的 README、LICENSE/NOTICE/署名、安装入口和用户示例，不为原本没有的自用 Skill 强造空壳。
4. 详细判据放进按需 reference，确定且重复的工作放进无额外运行依赖的脚本；Agent metadata 保持薄层，不复制业务合同。
5. 任何死重删除先在隔离发行副本完成完整确认链；移除第三方内容时复核 LICENSE/NOTICE。用户确认前不修改权威源码。
6. 若需要修软链，逐条给出明确源、目标和预期 `realpath`，逐条执行、逐条复核；禁止批量猜路径。
7. 不默认 commit、push、发布、安装依赖或执行未知目标代码。

## 真实运行验收

自动检查只能证明静态合同和确定性门禁。完成必须包含：

1. 从临时干净发行包重建并双向校验 manifest。
2. 重跑静态审计、单元测试、目标 Skill 自带 doctor 和代表性构建；这些运行必须已获用户授权且在隔离环境中进行。
3. 使用全新 Agent 会话，从明确安装入口真实调用目标 Skill，完成一个代表任务。
4. 比较改动前后的用户可见结果；记录输入、预期结果、失败信号、绝对路径或 URL。
5. 将 `macOS/Windows × Agent × 入口` 每格标为“已验证支持”“明确不支持”或“尚未验证”。平台/Agent 未实测就保持“尚未验证”。
6. 清理临时发行目录、报告、缓存和辅助进程，不在仓库遗留垃圾。

`runtime_verification=not-run` 时必须明确写“静态审计已完成，真实 Agent 运行尚未验证”，不能交付为全链路完成。

## 交付

先说结果，再说明：改了什么和保留什么；公共根因与生命周期边界；源码、发行和安装入口的绝对路径；实际运行的命令与结果；死重候选是否只停留在候选；平台/Agent 验证矩阵；残留风险、人工验收步骤、临时产物清理状态，以及 commit hash/服务 URL（如有）。

如果用户没有确认修改，最终必须标记“只读审计，未改文件”。
