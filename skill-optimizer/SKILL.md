# Skill Optimizer

## 质量内核

把 Skill 当成可执行产品：接口明确、依赖可解释、一个规则一个主人，并以可验证成品收尾。依赖允许存在，但必须说明用途、阶段、体积、引入路径，以及无依赖替代是否真的成立。

优化不是只让 Agent 少读文件。必须同时保证用户拿到的发行包可使用，并保留优化前已经存在的用户说明、许可证和来源信息。

每次只处理一个目标 Skill。优化后只保留唯一现行合同；删除旧入口、旧命令、fallback、迁移说明、失效示例和废弃资源。历史交给 Git，不在 Skill 中保存多套活跃版本或自动备份。

不要为缩短内容而删除必要的正确性、安全、权限或数据保护规则。能合并时把它们收敛到一个权威位置。

## 选择模式

- 用户说“审计、诊断、评估”时保持只读，只交付问题、影响和建议。
- 用户说“优化、精简、修复”时先交付人话方案，等待用户明确确认后再改文件。
- 用户尚未确认时，不写文件、不删除内容、不展示大段 diff。
- 目标任务、用户群或核心输出需要改变时，说明这已是新 Skill，改用 `skill-creator` 重建，不静默改造。

## 先拆角色、载体和成本

审计前先区分谁维护、谁发布、谁安装、谁执行，不能把一个目录当成全部事实：

- **开发者**承担源码、测试、生成器、开发文档和开发依赖；它们可以留在 Git，不因此进入用户发行包。
- **发布层**把源码变成可安装的目录或压缩包；发布内容、版本和校验必须可复现，不默认等于 Git 工作区。
- **使用者**只承担安装后的文件和完成用户任务必需的运行依赖；开发、测试和打包依赖不得转嫁给使用者。
- **Agent/模型**只消化 metadata、触发后的 `SKILL.md` 和任务实际读取的引用；仓库文本总量、下载体积和模型上下文是三种不同成本。

至少分开核对五个载体：远端源码版本、本地开发工作区、发布产物、本地安装副本、实际运行环境。`在 Git 中保留`、`进入发行包`、`模型会读取`、`用户必须安装`是四个不同结论，禁止互相推导。

所有依赖按主要阶段归类为开发/测试、构建/CI、发布打包、用户运行时或可选能力。不能归类时标记“待验证”；不要仅凭文件名、体积或单次缺失就要求删除文件、迁移语言或安装系统软件。

依赖决策固定按“系统原生能力 → 已有依赖 → 新增依赖”推进。原生替代只能作为候选，必须同时证明调用路径、功能等价与回归结果：Node 18+ 的全局 `fetch` 不覆盖 Undici 的 Agent/ProxyAgent/MockAgent 等专有能力；`node:zlib` 只替代 Node 路径中的压缩用途；UTF-8-only 合同不能靠猜测排除多编码支持；两套解析器只有进入同一入口且职责重叠才建议合并；Chrome 打印只有覆盖 `pdf-lib` 的全部实际能力后才构成替代。审计器不自动删除依赖。

### 用户发行包外壳

发行包不设统一的 README 或许可证强制清单。个人自用、未对外分发的 Skill 可以只有 `SKILL.md` 和运行必需资源；源码与发行包原本都没有 README 或许可证时，不因此判失败，也不要为了通过检查生成空壳文件。

先盘点优化前的源码和已发布内容，再确定发行外壳：

- 原本存在的根目录 `README.md`、安装说明或快速入口，默认继续保留；可以在不损害用途、安装、依赖、平台边界和有效链接的前提下精简。
- 原本存在的 `LICENSE`、`COPYING`、`NOTICE`、`ATTRIBUTION`、第三方声明和版本/来源信息，默认继续保留；不得用减少上下文或包体作为删除理由。
- `SKILL.md`、Agent metadata、运行脚本、直接引用及完成用户任务必需的资源按实际运行合同进入发行包。

README 和许可证即使属于发行外壳，也不会因为未被 `SKILL.md` 引用就进入模型上下文。**不进入模型上下文不等于应该从发行包删除；原本没有也不等于必须新增。**

大型展示样例、完整图册、测试和生成器可以留在开发仓或展示站；但原本面向使用者的示例或入口不能仅因瘦身被清掉，移动文档和素材后必须重写并验证所有相对链接。不得仅凭 `README`、`LICENSE`、`NOTICE`、`ATTRIBUTION`、`examples` 等名称把文件判为开发垃圾。确需移除既有文件时，必须给出当前发行合同、替代入口、许可证依据和用户确认，不能由优化器自行推导。

声明多个系统或 Agent 时建立 `macOS/Windows × Agent × 入口` 矩阵，每格只能是“已验证支持”“明确不支持”或“尚未验证”。文档、静态扫描和相似内核不能代替真实运行验证。业务合同只有一份；平台启动器和 Agent metadata 只能是薄适配层，不复制业务逻辑。

## 确定入口与边界

1. 确认目标 `SKILL.md`、输入路径和 `realpath`；查找权威源码、发布产物及安装副本，说明它们是同目录、符号链接还是独立副本。
2. 查找目标所在 Git 仓库并检查状态、HEAD 和本地 upstream 快照。需要当前远端事实时再做只读远端核对；不得把本地 remote-tracking ref 当成实时远端。
3. 保留无关改动；目标文件存在重叠未提交修改时暂停确认。未处于 Git 管理且需要删除或覆盖内容时，说明无法依靠 Git 恢复并等待确认；不要自动创建旧版副本。
4. 以用户本次要求和当前有效交付行为确定唯一现行合同。文件互相冲突且无法判定权威时，只问一个能解除阻塞的人话问题。
5. 先用文件清单、Git 元数据和入口调用关系确定影响面，再定点阅读目标 Skill、直接引用、依赖清单、发布配置、运行脚本、资源和 `agents/openai.yaml`。不要因为仓库很大就全文读取无关源码，也不要因文件不在 `SKILL.md` 引用链就忽略真实运行依赖。

发行瘦身不得顺带改变权威源码、仓库入口或镜像关系。独立仓库、单仓目录和发行镜像之间的主人变更属于单独架构决策，必须有当前合同、同步机制和用户确认，不能从“包太大”推导出来。

## 系统性诊断与反补丁门禁

六层是观察维度，以下证据链才决定能否进入实施。用户给出的截图、旧结论或单个案例只是复现材料，不自动等于当前事实或完整影响范围。

1. **问题合同**：写清角色、载体、目标平台/Agent、预期行为、实际行为、最小复现和失败信号；无法复现时说明证据缺口。
2. **因果定位**：沿安装入口、公开命令、直接引用、脚本、外部命令、资源和最终输出追踪；区分环境故障、包内容故障与业务输出故障。
3. **公共根因与影响面**：区分表面症状、直接原因、公共根因和促成条件；枚举共享同一规则主人或失败机制的入口。
4. **权威修复与防复发**：在源码、发布、适配器或运行时中修正真正的规则主人；用同一复现证明修改前失败、修改后通过，再验证同类代表案例。

出现以下任一情况，不得称为“系统性修复”：把开发仓库直接当用户包；把测试或生成器简单称为无用内容；把“模型不读取”推导成“发行包不携带”；未核对优化前状态就移除既有 README、许可证、署名或用户示例；为原本没有这些文件的自用 Skill 强造空壳；只补用户点名的命令、系统或 Agent；借发行瘦身改变权威源码；用新增 fallback 掩盖错误合同；只凭结构审计、单个测试或一次成功输出代替真实安装与运行验证。

确需先止血时，明确标记为“临时缓解”，保留诊断证据并写清后续根因任务和移除条件；临时缓解不能作为完整修复关闭。

## 运行确定性审计

先运行只读审计器，再按发现定点阅读文件。已知源码路径时一并比较：

```bash
python3 <本 Skill 目录>/scripts/audit_skill.py <目标 Skill 目录> \
  --surface <source|release|installed> \
  --profile <auto|general|review> \
  --supported-node-majors 22,24 \
  --source <权威源码 Skill 目录> \
  --metafile <esbuild metafile 路径> \
  --format json
```

`--source` 和 `--metafile` 可省略；未显式提供 metafile 时只查找常见文件名。载体无法确定时使用默认 `--surface auto`，此时不得给出删除建议。`--profile auto` 在 `release` 载体自动使用 `review`，其他载体使用 `general`。`--supported-node-majors` 由 Agent 根据当前官方 LTS 支持矩阵查询后传入；审计器自身保持离线，不把内置默认值冒充实时官方事实。

`review` 会联合检查 SKILL/README、`package.json engines`、doctor/constants 和测试矩阵中的版本门槛；流式分析 1 MiB 以上文件，不再因体积跳过；区分源码、生成 bundle、压缩代码和“有多项强证据的疑似混淆”，没有证据时不得直接称为混淆。它还按自有代码、第三方代码、数据、字体、示例和文档报告发行占比。超过体积或文件预算只要求解释，不会把大型 Catalog、字体或用户示例自动判为垃圾。

依赖归因优先使用 `package.json`、npm lockfile、源码 import 和 esbuild metafile，输出直接/传递、开发/运行、外置/内联和字节占比。联网行为只沿公开 doctor/build/install 等入口做静态检查并按测试开发、构建发布、用户运行时归类；未知 Skill 的 doctor/build/install 不自动执行，审计器不联网、不安装依赖，也不根据线索自动删除内容。Node 原生能力和 esbuild 归因边界以 [Node Globals](https://nodejs.org/dist/latest/docs/api/globals.html)、[Node zlib](https://nodejs.org/api/zlib.html) 与 [esbuild Metafile](https://esbuild.github.io/api/#metafile) 为依据。

`--surface release` 会把目标视为用户发行包并检查文档断链；同时提供 `--source` 时，还会检查源码原有的 README 和许可证是否被发行瘦身清掉。源码与发行包原本都没有这些文件时不报错；发行包仅缺少测试、生成器等开发文件属于正常裁剪，不再把整棵源码差异误报为安装漂移。Finding 保留原字段，并可增加 `surface`、`kind=fact|candidate|policy` 与 `confidence=high|medium|low`。退出码 `0` 只表示当前所选载体没有结构性阻断，不证明业务或跨平台运行正确。

- `0`：审计完成且没有结构性阻断。
- `1`：审计完成但存在断链、非法入口等阻断问题。
- `2`：参数、目标路径或运行本身失败。

token 只估算声明可达的模型上下文上限；目标文件字节数、Git 跟踪体积和用户发行包体积分别报告，禁止合并成“用户消化成本”。

## 按六层诊断

完成证据链后，把发现映射到以下六层：

1. **权威合同**：角色、源码、发行、安装、入口、输出和依赖是否各有唯一主人；优化前存在的人类说明、许可证和来源是否被保留。
2. **正确性**：主路径、边界、失败处理及目标平台/Agent 能否同时成立。
3. **职责结构**：规则是否 MECE；共享核心与薄适配器是否分开。
4. **上下文与载荷成本**：模型上下文、下载包体、磁盘占用和 Git 历史是否分别合理。
5. **执行与依赖成本**：是否把开发依赖转嫁给用户，或存在无效提问、全仓读取、重复试错和可脚本化工作。
6. **交付闭环**：是否从发布产物或干净安装环境完成真实任务，并给出路径、版本、验证和残留风险。

区分相近问题：跨文件或优先级互相打架是冲突；同一合同无法同时满足是矛盾；相同表达再次出现是重复；即使只出现一次但没有执行价值也是冗余。

## 先给人话方案

只输出用户做决定需要的信息：

```markdown
结论：<整体问题和处理方向>
根因：<公共根因及证据；未证实时写待验证>
角色与载体：<开发者、发布层、使用者分别承担什么；源码、发行、安装、运行是否一致>
影响面：<平台、Agent、入口和同类机制>
保留：<留在 Git、发行外壳、运行核心和展示层的内容>
要处理：<准备删除、排除、打包、移动或改写什么>
为何不是补丁：<权威修复点和防复发门禁>
改善：<上下文、下载、安装和运行分别改善什么>
风险：<未验证平台、Agent 或发布链>
验证：<修改前失败、修改后通过、干净安装和同类代表检查>
确认：<请用户确认以上改动>
```

不要默认列提交图、原始 JSON、大段 diff 或术语清单。对每个文件和依赖先说明“留在 Git、进入发行、运行必需、可选或待验证”，再谈删除或替换。

## 确认后实施

1. 再次检查源码和安装副本状态，确认用户改动边界没有变化。
2. 在已证实的规则主人执行最小完整改动；由同一根因造成的错误散落多处时一次清完，范围外保持不变。
3. 开发资产按职责留在源码；发行包排除开发专用内容，但不得仅为瘦身删除优化前已有的 README、许可证、适用声明和用户入口，也不为原本没有的自用 Skill 强制新增。只有失效入口、重复规则、废弃资源和已被推翻的示例才删除；移动展示内容时同步修复链接。
4. 将详细条件知识放入按需引用，将重复且确定的工作放入无额外依赖的脚本；不要为形式完整新增空目录或辅助文档。
5. 同步 `agents/openai.yaml` 及必要的 Agent 薄适配器，业务正文保持唯一。
6. 重跑原始复现、同类案例、目标测试、结构审计，并从发布产物或独立安装副本验证用户主路径。平台/Agent 未实测就保持“尚未验证”。
7. 不默认 commit、push、发布或安装系统软件；只有用户明确要求时才执行。

## 交付

完成后先说结果，再给：

- 改了什么，哪些开发资产、用户能力和共享核心被保留。
- 公共根因、角色/载体边界、同类影响面，以及为何不是局部补丁。
- 源码、发布产物和安装副本的绝对路径与同步状态。
- 实际运行的检查、修改前后失败信号，以及 macOS/Windows 与 Agent 验证矩阵。
- 声明上下文、目标载荷和发行包体积的前后对比；无法取得发行包时明确写“未验证”。
- 发行外壳中的 README、许可证、声明、示例入口和相对链接在优化前后的保留结果；原本不存在时明确写“不要求新增”。
- 仍有风险、人工验收步骤和临时产物清理状态。

如果用户没有确认修改，最终交付必须明确标记为“只读审计，未改文件”。
